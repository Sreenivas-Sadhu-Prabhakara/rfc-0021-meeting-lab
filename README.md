# RFC 21 — Meeting follow-up register

**Covered RFC 21. Next RFC 22 — Host-host control message formats.**
This lab follows the [published RFC 20 source](https://github.com/Sreenivas-Sadhu-Prabhakara/rfc-0020-ascii-lab/commit/213455e2430ea5539a060cb733eb8863b7fddb3d)
and reuses its Go module layout, CLI conventions, MIT license and CI workflow.

## What RFC 21 records

Vint Cerf published these minutes on 17 October 1969, one week after the
UCLA network meeting with representatives from UCLA, SDC and UCSB.
The memo records reported changes to BBN Memo 1822, including transmit
and receive link limits, a discussion about idle link expiry and a
measurement message discarded before reaching the destination host.
It also points to RFC 22 for changes to the work in RFC 11 and names
George Gregg as the person who will publish RFC 23 on multiple control messages.

The RFC Editor records RFC 21 in the Legacy stream with publication and
current status Unknown, and empty formal updates, updated-by, obsoletes
and obsoleted-by fields as checked on 13 November 2026. The mentions of
other documents are references in the minutes. This administrative
record motivates a modern decision and follow-up register.

- [Official RFC Editor text](https://www.rfc-editor.org/info/rfc21/)
- [Official metadata](https://www.rfc-editor.org/rfc/rfc21.json)

## Applications

- **Banking API migration reviews.** Track whether gateway and downstream
  teams assigned an owner and a date to each action.
- **Cloud cutover planning.** Keep rollback questions distinct from
  approved decisions and require evidence for claimed completion.
- **Standards study.** Trace meeting notes back to the source section and
  identify follow-ups that the meeting recorded without a deadline.

## Run

Use Go 1.22 or later from the repository root.

```sh
go run ./cmd/meetinglab < examples/rfc21.json
go run ./cmd/meetinglab -html < examples/rfc21.json > docs/index.html
go test -race ./...
go vet ./...
go build ./...
```

The fixture paraphrases five entries as of the memo's publication date.
It records three notes, one question and one action. The publication action
has a named owner and no recorded deadline. A separate decision category
remains empty for this editorial classification of the fixture.

## Input and checks

Supply one JSON object on standard input, up to 64 KiB, with a nonblank
title, an explicit ISO date in `as_of` and 1–200 items. Each item needs a
unique lowercase ID, a kind (`decision`, `question`, `note`, or `action`),
a nonblank summary and a source locator. IDs begin with a letter and may
contain lowercase letters, digits or hyphens up to 32 characters.

Action items can carry an owner, ISO date in `due`, boolean `done` and
completion evidence. An action is overdue when its deadline falls before
`as_of`. A completion claim with blank evidence is unverified. With
nonblank evidence it is closed. Evidence is an assertion recorded in
the input, and the operator is responsible for verifying it.

Malformed input exits nonzero with an error. A valid report with findings
exits successfully so it can be reviewed in JSON or HTML. Explicit kinds
make categorization auditable and require a human to interpret the minutes.
This tool uses a modern review schema and sample data derived from the memo.
GitHub Pages serves the static report generated by Go. The CLI runs locally.

Tests cover categories and source preservation, overdue boundaries,
incomplete ownership and deadlines, unverified completion claims, invalid
input, and HTML escaping. CI checks the generated page against the
committed HTML.
